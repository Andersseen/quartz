# 0.24 — Consumer toolchain compatibility, release acceptance enforcement and 0.16.1 readiness

**An engineering milestone, not an npm release.** No `@quartz-headless/*@0.24.0` exists or will be published from this work. The package manifests stay at
the prepared `0.16.1` candidate (the maintainer's patch decision of 2026-11-16 stands); the latest **published** version is still `0.16.0`. The public API
stays a freeze candidate; nothing was frozen. Acceptance record: [0.24-readiness-acceptance.md](../releases/0.24-readiness-acceptance.md).

## 1. The weekly failure

The weekly `CI / CD` run [45189626879](https://github.com/Andersseen/quartz/actions/runs/45189626879) (2026-11-23) failed in exactly one job,
`Consumer angular-21.2-min / Node 20.19.0` (job 137744581775). Everything else, including the Node 24 and Node 22 consumer cells, the CLI consumer and the
three E2E shards, passed.

### What actually failed

The job installs the repository with Node 22, verifies the release artifacts, then switches the **whole runner** to Node 20.19.0 and runs
`pnpm verify:consumer:runtime -- --fixture angular-21.2-min`. Since 0.23, `scripts/consumer/run.mjs` started that consumer by running **repository Vitest**
(`pnpm exec vitest run --project quartz-app src/app/docs-playgrounds/usage-code.spec.ts -t "generates strict consumer compilation fixtures"`) to write the
playground examples. Vitest failed while loading its own project configuration:

```
failed to load config from vitest.app.config.ts
TypeError: Cannot read properties of undefined (reading 'async')
    at ModuleLoader.importSyncForRequire (node:internal/modules/esm/loader:300:22)
    at loadESMFromCJS (node:internal/modules/cjs/loader:1371:24)
    ...
    at Object.<anonymous> (vitest.app.config.ts:23:235)
```

So the consumer never reached `npm ci`, let alone Angular AOT. Quartz's packages and Angular 21.2.0 were never executed.

### Root cause

1. The repository root `package.json` has no `"type": "module"`, so Vite 8.0.8 bundles `vitest.app.config.ts` to **CommonJS**. Externalized imports become
   `require()` calls; line 23 of the bundled config is `require(".../vite@8.0.8/.../vite/dist/node/index.js")`. Vite is ESM-only, so this is a
   `require(esm)` (unflagged since Node 20.19.0).
2. Vitest 4.1.2 loads its five project configs concurrently while the ESM loader is still importing Vite. The `require()` finds Vite's module job in the
   ESM loader cache before that job has linked its module.
3. Node **20.19.0**'s `importSyncForRequire` dereferences `job.module.async` without checking that `job.module` exists
   ([v20.19.0 source](https://github.com/nodejs/node/blob/v20.19.0/lib/internal/modules/esm/loader.js#L298-L300)). Later Node lines guard this race
   explicitly (v20.20.2 asserts `if (!job.module)` with a "race" message referencing node:55782 and also handles the `kInstantiated` state).

It is a timing-dependent race in the Node runtime's `require(esm)` path, triggered by repository tooling. See the acceptance record for the reproduction
statistics. Installed versions at the time: Node 20.19.0, Vitest 4.1.2, Vite 8.0.8, `@analogjs/vite-plugin-angular` 2.9.2, Angular 21.2.6 (repository) /
21.2.0 (consumer), TypeScript 5.9.3, jsdom 27.4.0.

The defect is **not** a Quartz incompatibility with Node 20. With the boundary below, the same Angular 21.2.0 consumer installs, compiles (strict AOT,
SSR) and serves on Node 20.19.0, and the three-engine suite passes.

Why it surfaced only now: push and PR events skip the deep matrix. The 2026-11-09 and 2026-11-16 weekly runs failed earlier for an unrelated reason
(`ubuntu-latest` moved to 26.04, which Playwright does not support; fixed by pinning `ubuntu-24.04` in PR #60/#61). 2026-11-23 was the first weekly run
that reached 0.23's Vitest-based fixture generation on Node 20.19.0.

## 2. The toolchain boundary

`scripts/toolchain.mjs` defines two kinds of processes:

| Concern            | Runs                                                                                                 | Node                                                          |
| ------------------ | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Repository tooling | pnpm, Vite/Vitest/Analog, playground fixture generation, the consumer harness, the Playwright driver | `^22.12.0 \|\| >=24` (CI: 22), asserted by the scripts        |
| Consumer runtime   | `npm ci`, the tarball install, `ng build` (strict AOT + SSR, incl. negative builds), the SSR server  | the matrix cell's Node (20.19.0 / 24 / 22), passed explicitly |

- `scripts/consumer/run.mjs` asserts it runs on the repository Node. It takes `--consumer-node <binary>` (default: its own Node) and
  `--expect-consumer-node <spec>`. Every consumer command runs on that binary: npm from the same installation (its bin directory is first on `PATH`), `ng`
  as `<consumer-node> node_modules/@angular/cli/bin/ng.js`, the server as `<consumer-node> serve.mjs`. After `npm ci` the harness asks npm which Node it ran
  on (`npm version --json`) and fails unless it is the consumer Node. The evidence JSON records both `node` (consumer) and `toolchainNode`.
- In `deploy.yml` the consumer-matrix job generates fixtures on Node 22, sets up the cell's Node only to capture its binary path
  (`QUARTZ_CONSUMER_NODE`), restores Node 22, and passes `--consumer-node "$QUARTZ_CONSUMER_NODE" --expect-consumer-node ${{ matrix.node }}`. Node 20 is
  still a matrix cell; nothing was replaced by Node 22.

## 3. Generated fixture strategy

- `src/app/docs-playgrounds/consumer-fixtures.ts` holds the pure `buildConsumerFixtures(registry)` and the nine-family variant table that used to live
  inside the Vitest spec. It fails loudly when the variant table and `DOC_PLAYGROUNDS` drift, when a generator is not deterministic, or when an example is
  malformed. `usage-code.spec.ts` tests it against the real registry.
- `scripts/consumer/playground-fixtures.mjs` evaluates the **real** `registry.ts` and the builder with Vite's module runner (`runnerImport`). There is no
  Vitest and no test-name filter. Playground component modules are replaced by inert classes named after their own `export class` declarations (derived from
  the files, not a hand-kept copy). It writes 18 Component variants + `index.ts` and a `fixtures-manifest.json` (sha256 per file, variant list, digest of
  the playground sources). It refuses to run on Node 20 and to write inside the repository.
- `verifyFixtures` rejects a missing manifest, missing, edited or unlisted files, a variant count other than 18, and **stale** fixtures (sources changed
  since generation). The harness verifies before copying them into the disposable consumer, which then compiles them with its own Angular toolchain and
  Node under strict AOT (`strict`, `strictTemplates`, `skipLibCheck: false`). The negative compiler checks are unchanged.
- The generated output is byte-identical to the 0.23 Vitest-generated fixtures (verified with `diff -r`).

## 4. Release acceptance enforcement

### Preflight

`pnpm release:preflight` (`scripts/release/preflight.mjs`, pure logic in `scripts/release/acceptance.mjs`) is read-only. It reports PASS, BLOCKED or WAIVED
for: lockstep package versions, the Core peer (repository and packed), source commit identity, the release manifest and its sha256, every required CI job's
result, the acceptance record, each manual gate (screen reader; Autofill in Firefox and Safari), `npm-release` environment protection, maintainer approval
and the registry state (via the existing fail-closed `planPublication`). It exits non-zero while anything is BLOCKED.

- Acceptance stays in the existing record (`docs/releases/<version>-acceptance.md`) as one fenced `json release-acceptance` block. There is no new status
  database. An `executed` gate must name a full `testedCommit` that is an ancestor of the release commit with no `packages/` change since, plus a tester and
  date, and the referenced rows of `docs/releases/0.17-manual-a11y.md` must actually be `PASS`. Autofill must accept the `firefox` and `safari` scope.
- A `waived` gate needs a GitHub login, a date, a reason and the candidate version. Text alone never counts: the waiver is honoured only when **that login
  approved this workflow run's `npm-release` deployment**.

### Human authorization

- The `publish` job deploys to the GitHub environment `npm-release`. With required reviewers configured, GitHub pauses the job until a reviewer approves
  the run. That approval is the only authorization signal. It is not a file and cannot be granted by a commit.
- `release-acceptance` (new job, no secrets) runs the preflight in `pre-approval` mode after every required job. On a publishing dispatch, BLOCKED fails it
  and `publish` never starts. On a non-publishing dispatch it only reports.
- Inside `publish`, after approval, the preflight runs in `publish` mode. It reads `/actions/runs/{id}/approvals`, requires an approval from a user listed as
  a required reviewer of `npm-release`, re-checks the environment (it must exist, have user reviewers, have admin bypass off and restrict branches) and binds
  the result to version, commit, manifest sha256 and run id. `release.mjs publish` refuses without that file, or if any binding differs, before contacting
  the registry.
- Naming an environment in YAML does not protect it. GitHub creates a missing environment **unprotected** when a job first references it. The preflight
  therefore checks the configuration through the API and blocks when it is missing or weak.

### Current GitHub state (read 2026-11-27, not changed by this work)

The `npm-release` environment **does not exist**, and `main` has **no branch protection**. The preflight reports `environment-protection: BLOCKED`.
Publication is blocked until the maintainer completes RELEASE_RUNBOOK §0.1. An agent must not create or approve this configuration on the maintainer's
behalf.
