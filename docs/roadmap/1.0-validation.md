# Beta → RC → 1.0

Estado: propuesta. Entrada: 0.11 aceptada y contrato congelado.
Responsable: producto + orquestador + integrador/release manager.
Aquí se valida adopción y el artefacto, no se añade catálogo ni se rediseña API.

## V1-REL-01 — Preparar beta utilizable

- **Rol:** release manager prepara; publicación únicamente bajo autorización vigente.
- **Entrada:** acta 11-07, tarballs verificados, canal prerelease correcto, migraciones y
  checklist conocido. Respetar el peer de Core para la versión beta exacta.
- **Salida:** versión candidata y instrucciones de instalación con versiones precisas,
  flujos a probar y mecanismo de feedback. No basta distribuir un enlace al repositorio.
- **Aceptación:** un consumidor puede instalar desde cero sin resolver manualmente peers ni
  importar rutas internas. Si falta autorización externa, preparar todo y registrar ese estado;
  no llamar «publicada» a una beta local.

## V1-REL-02 — Dos integraciones independientes

- **Rol:** integrador coordina, implementadores consumidores siguen encargos acotados.
- **Proyecto A:** app CRUD/forms con Select/Checkbox/RadioGroup/Switch, validación, Dialog,
  Menu y notificaciones; estilos propios.
- **Proyecto B:** app SSR/hidratada con Tabs/Accordion, contenido dinámico y overlays tras
  hidratar; servir varias peticiones y navegar. Diferente workspace y sin aliases a fuentes.
- **Registrar por proyecto:** versiones Angular/Node/Quartz, commit, casos probados, dificultad
  de integración, dependencias, bugs y workaround. Priorizar una app real existente si está
  disponible; no simular su aceptación usando solo las demos de Quartz.
- **Aceptación:** todos los requisitos aplicables cerrados; ningún parche de Quartz local;
  operador/consumidor acepta integración. Objetivo de dos semanas de uso, con evidencia y no
  solo calendario. Si no se dispone de consumidores, mantener la beta; no inventar feedback.

## V1-REL-03 — Triage y cierre de beta

- **Rol:** orquestador clasifica; implementador recibe una regresión por encargo.
- **P0/P1:** corregir antes de RC, añadir regresión y repetir escenarios afectados.
- **Ruptura de contrato:** evaluar si spec o implementación estaban equivocadas. Una API nueva
  necesita decisión explícita, migración, nueva beta y revalidación; no esconderla como fix.
- **P2/P3:** mejoras compatibles no necesarias para cumplir contrato pasan a backlog posterior.
  Un problema etiquetado P2 que rompe una promesa estable sigue bloqueando 1.0.
- **Aceptación:** acta de beta con casos/defectos/resoluciones, contratos congelados o cambio
  explícitamente revalidado; cero trabajo imprescindible desplazado sin resolución.

## V1-REL-04 — Candidato RC reproducible

- **Rol:** integrador y release manager; revisor comprueba evidencia.
- **Trabajo:** construir candidato y registrar hashes; ejecutar quality, units/cobertura,
  contratos, builds, consumers AOT/SSR, CLI y E2E/compatibilidad; revisar a11y manual realizada.
- **Estabilidad de suite:** cinco ejecuciones completas consecutivas sin retries del candidato,
  con versiones/entorno documentados. Investigar fallos; no relanzar hasta obtener cinco verdes
  ignorando la causa. Un flaky conocido de release debe corregirse.
- **Aceptación:** matriz completa sobre ese candidato; no cambios fuente pendientes; tarballs,
  metadatos, migración y runbook listos. El tiempo sin reportes no sustituye esta evidencia.

## V1-REL-05 — Publicar y verificar 1.0

- **Rol:** responsable de release, con autorización de publicación.
- **Preflight:** checklist final del ROADMAP, versiones/peer ranges definitivos y release notes.
  Cambiar de RC a estable implica un artefacto con nueva versión: volver a empaquetar y ejecutar
  gates sobre el artefacto estable. No afirmar identidad binaria con RC si cambió el manifiesto.
- **Publicación:** Core antes de Primitives, verificación de la pareja y promoción de canales
  según runbook; GitHub release y docs alineadas. No adelantar anuncio estable a una pareja parcial.
- **Comprobación posterior:** instalación desde registro con versiones exactas en proyecto limpio,
  AOT y flujo mínimo; enlaces/API docs/changelog correctos. No confundir publicación aceptada
  por npm con instalación verificada.
- **Salida:** acta con versiones, hashes, comandos/resultados, fecha, responsable y límites de
  soporte. Tras 1.0 aplicar la política SemVer aprobada y usar nuevas versiones para correcciones.

## Trabajo posterior a 1.0

Cada familia excluida necesita demanda, spec, pruebas y revisión de API antes de entrar en una
minor `1.x`. Posibles candidatos: Combobox/Tree avanzados, interacción accesible DnD, virtualización
avanzada, Slider, layout o CLI distribuida. No prometerlos en la fecha de 1.0 ni introducir un
export incompatible en una minor estable.

La responsabilidad del orquestador continúa: proteger el contrato publicado y reducir el
alcance de cada encargo, aunque haya más modelos disponibles para escribir código.
