# 0.11.0 — Distribución y API congelada

Estado: propuesta. Entrada: gate de consumidores 0.10.
Correspondencia: REL-01…03, DOC-02…03 y API-05. Responsable: release manager + orquestador.
El trabajo prepara un proceso revisable; publicar sigue siendo una acción externa separada.

## Orden

`11-01 → 11-02 → 11-03 → 11-04`; `11-05` y `11-06` consumen contratos cerrados.
Todos preceden a `11-07`.

## 11-01 — Mismo artefacto validado y distribuido

- **Responsable:** implementador tooling; revisa release manager.
- **Archivos:** `package.json`, `packages/*/ng-package.json`, `scripts/verify-build.js`,
  smoke/fixtures y `.github/workflows/deploy.yml`, según la estrategia aprobada.
- **Contrato:** construir/pack una vez; verificar/instalar ese tarball; conservar hash y commit;
  publicar ese artefacto. Si se reconstruye, comparar identidad antes de publicación.
- **Aceptación:** README/LICENSE presentes, exports/tipos correctos, Core externo en Primitives,
  metadatos/versiones correctos. Un tarball manipulado después de verificación debe rechazarse.
- **No hacer:** verificar un dist y publicar otro reconstruido sin control de equivalencia.

## 11-02 — Versionado y prereleases

- **Responsable:** implementador release; contratos del responsable técnico.
- **Casos:** estable, beta, RC, versión ya publicada, mismatch entre Core/Primitives, peer de
  Core incompatible con la versión compañera, consulta npm fallida.
- **Aceptación:** canales `next`/`latest` explícitos; GitHub prerelease para beta/RC; core peer
  satisface la versión exacta instalada, incluidas prereleases (probar con semver, no asumir
  que un caret estable acepta prereleases). Changelog y versión forman una unidad revisada.
- **No hacer:** tratar error de red/token como «versión libre»; corregirlo reintentando publish.

## 11-03 — Publicación parcial y recuperación

- **Responsable:** orquestador diseña procedimiento; implementador automatiza partes seguras.
- **Casos:** Core publicado y Primitives falla; ambos publicados pero GitHub release falla;
  rerun del mismo workflow; dos intentos simultáneos; fallo de un check previo.
- **Aceptación:** rerun idempotente sobre los mismos artefactos; no sobrescribir una versión
  publicada; impedir publicación concurrente conflictiva; reconciliar pareja de paquetes
  antes de promocionar estable; fallo de cualquier gate bloquea la promoción.
- **Salida propuesta:** `docs/releases/RELEASE_RUNBOOK.md`, con recuperación paso a paso.

## 11-04 — Ensayo de release y hotfix

- **Responsable:** integrador/release manager; prueba aislada sin publicar versiones reales.
- **Trabajo:** probar metadatos y decisiones con fixtures/mocks o registro local controlado;
  simular fallos de 11-02/03; comprobar que permisos/tokens no se imprimen en logs.
- **Hotfix:** reproducir regresión, corregir con test, patch compatible, matriz afectada más
  gates de release, nueva versión. Si altera contrato, evaluar SemVer antes de etiquetar patch.
- **Aceptación:** runbook ejecutable por otro modelo/operador con resultados esperados y
  puntos de parada; no usar npm real como entorno de ensayo ni confiar en rollback de versión.

## 11-05 — Documentación para consumidores

- **Responsable:** modelo de documentación; QA verifica ejemplos.
- **Áreas:** README, docs de compatibilidad, páginas/snippets y guía de migración; evitar
  rediseños visuales. Asignar una familia por encargo.
- **Por área:** objetivo, instalación/import, host permitido, ejemplo mínimo accesible,
  inputs/models/outputs con defaults, métodos, teclado/ARIA, hooks CSS/DOM, SSR y limitaciones.
- **Casos integrados:** formulario validado, popup en Dialog, contenido dinámico, actualización
  externa y uso con estilos propios. No depender de Volt/lumen para demostrar uso de Quartz.
- **Aceptación:** ejemplos compilan en fixture de consumidor; nombres de API coinciden con
  declarations; guía `0.5→1.0` cubre cada retirada/cambio y permite ejecutar la migración.

## 11-06 — Soporte y contribución mantenibles

- **Responsable:** producto/orquestador decide políticas; modelo de documentación redacta.
- **Contenido:** plataformas/versiones soportadas, tratamiento de deprecaciones, información
  mínima de bug report, contribución con spec/tests, reporte de vulnerabilidades y limitaciones.
- **Alinear instrucciones:** actualizar la regla de `BEST_PRACTICES.md` que limita E2E a la
  demo: con 0.10 existen flujos consumidores AOT/SSR válidos. Mantener la distinción entre
  comportamiento browser y lógica que basta probar unitariamente. No dejar reglas contradictorias.
- **Aceptación:** otro colaborador puede reproducir y proponer un fix; soporte no promete SLA
  inexistente; no quedan instrucciones que apunten a la antigua distribución unscoped.

## 11-07 — Congelación formal

Orquestador revisa inventario de exports, contracts/tests y migraciones contra código final.
Integrador ejecuta matriz completa y ensayo. Responsable de producto acepta lista exacta de
capacidades y limitaciones. Registrar fecha/commit, no solo «API estable».

**Permitido después:** bugs compatibles, docs, mejora interna cubierta.
**Reabre congelación:** cambios en firmas, selectores, eventos, defaults, semántica de foco,
valores, DOM/hooks documentados o rango de soporte que rompan un consumidor válido.

Salida: candidato a beta y paquete de contexto para validación externa. Ningún modelo de
implementación publica automáticamente al marcar una tarea Done.
