# 0.21 — Deterministic E2E, browser reliability & release-validation confidence

**Status: E2E engineering milestone, not an npm release.** No package version changed (still `0.16.0`), nothing was published, the public API is a freeze candidate (not frozen), no 1.0 beta exists, and the manual screen-reader matrix is still pending. 0.17–0.19 still need their formal acceptance; 0.20 was website engineering only; 0.21 is E2E engineering only. Results and the open items are in the [0.21 acceptance record](../releases/0.21-e2e-acceptance.md).

## Goal

Make the documentation website's browser tests and the release quality gates reproducible **without depending on blind retries**: every failure must be explained by evidence (a defect fixed, or an environment fact recorded), never hidden by `retries`, a longer timeout or a `sleep`.

## What the evidence showed

The pre-0.21 suite was run unmodified (local defaults, no retries) before anything was changed. Seven distinct symptoms were investigated; they have **four different causes**, which is why "it was resource contention" was not accepted as a blanket answer.

### Why `networkidle` was removed

`networkidle` means "no network request for 500 ms". For this application that is neither necessary nor sufficient:

- **Not sufficient.** Demos are `@defer (on idle)`. In a measured Firefox load of `/docs/primitives/form-field`, `networkidle` resolved 465 ms after load and the deferred demo chunk (`controls-014.demo-*.js` plus three more) was requested ~500 ms _later_. A test that then looked for the demo raced the chunk.
- **Not necessary / unstable.** Each late chunk request restarts the 500 ms window, so a busy engine can keep extending it; `docs.spec` "health" waited for it 20+ times in a row and used `test.slow()` to survive.

### The readiness contract (`e2e/support/readiness.ts`)

A route is **ready** when all of these hold; every wait is a retrying web-first assertion, with no sleeps and no changed timeouts:

1. the document is the Angular app (`app-root[ng-version]`) at the requested path (redirects must be asserted explicitly);
2. **hydration finished claiming the server markup**: Angular removes each component host's `ngh` attribute when the client takes it over (`retrieveHydrationInfo`), and the raw prerendered HTML always carries them (29 on `/docs/primitives/select`). _No `[ngh]` left_ ⇒ every server-annotated component is live. `e2e/readiness.spec.ts` proves the raw HTML has them and the hydrated DOM does not;
3. the route's `<h1>` (optionally a specific name) is visible;
4. where a page has lazy demos, `waitForDemos` waits until no `.qz-demo-placeholder[aria-busy="true"]` remains (a demo or its explicit error fallback is the final state).

Fixtures follow the same rule: a `data-ready` marker is set from the browser only (signal + `isPlatformBrowser`), never in the static template. `readiness.spec.ts` fetches the raw HTML of every `e2e-*` fixture and fails if a readiness marker is present.

No site code uses `ngSkipHydration` to hide anything. (The pre-existing `e2e-navigation` _fixture_ host already opted out of hydration; that is unchanged.)

### First-failure diagnostics

Every test uses `e2e/support/test.ts`, a drop-in `test` with an automatic fixture. For a **failed or timed-out** test it attaches `diagnostics.json` (browser + version, Node, OS, CPU count, load average, free memory, worker/parallel index, worker count, retry, duration, final URL, navigation timing, console errors/warnings, page errors, failed requests, HTTP ≥ 400 responses). Query strings are stripped; no headers, cookies or bodies are captured. Traces are `retain-on-failure` (so they exist with `retries: 0`), screenshots on failure. The preview server writes failed responses, errors and lifecycle events as JSON lines to `e2e-logs/preview-server.log`. In CI, `playwright-report/` is always uploaded and `test-results/` + `e2e-logs/` are uploaded on failure.

### Production preview lifecycle

`playwright.config.ts` now starts `scripts/e2e/serve.mjs` instead of `pnpm build:demo && node …`:

- **Never partial output.** `build:demo` ends with the sitemap and Pagefind index and `vite build` empties the output directory first, so the served directory must contain `index.html`, `_redirects`, `sitemap.xml`, `robots.txt`, `docs/index.html` and `pagefind/pagefind.js`; otherwise the server refuses to start.
- **No overlapping builds.** A liveness-checked lock (`node_modules/.cache/quartz-e2e/build.lock`) makes a second builder fail fast.
- **Build modes** (`E2E_BUILD`): `always` (default; CI-equivalent), `reuse` (build only if incomplete), `skip` (never build; CI uses it after `build:demo && docs:check`, so the tested output is exactly the validated output).
- **No orphans.** SIGTERM/SIGINT are forwarded; the child is killed when the wrapper exits; the server drains on SIGTERM; Playwright uses `gracefulShutdown`.
- **Preview server hardening** (`scripts/preview-static.mjs`): malformed URLs → 400, handler errors → 500, `clientError` contained; keep-alive 120 s (Node's 5 s default races with browsers reusing a socket); files streamed with `content-length`; `HEAD`/405; containment check uses `root + sep`; more MIME types. Real 404s, `_redirects` and no SPA fallback are unchanged and covered by tests.

### WebKit

Findings, in the order they were established (details and numbers in the acceptance record):

1. The unmodified suite failed on WebKit in **synchronized bursts**: 5 workers hung at the same moment, three of them in the `beforeEach` `page.goto('/e2e-range')`. The same file failed in two independent full runs.
2. A trace of a hung `beforeEach` shows `page.goto` started and **no network entry at all**: the request never left the browser.
3. The preview server was ruled out: its log for the whole run contains only the three intended 404s, no errors, and replacing it with the hardened server did not change the outcome.
4. Later, `browserType.launch` itself timed out (180 s in Playwright, then 4 of 4 standalone `webkit.launch()` calls at 60 s) while Chromium launched in ~80 ms and Firefox in ~850 ms on the same machine, with no test or server code involved. `Playwright.app` starts and then sits idle at 0 % CPU.
5. The host was heavily oversubscribed by processes outside this repository: four `esbuild` daemons from other projects at 170–300 % CPU each for days, load average 12–30 on 10 cores, 4.6 of 6 GiB swap in use at one sample, `configd`/`audiomxd` at 30–60 % CPU.
6. A controlled comparison of `localhost` vs `127.0.0.1` as the base URL (suspecting resolver stalls) was **inconclusive**: the `localhost` run degraded massively (48 failures, 38.5 min) but the `127.0.0.1` run was stopped after the same stalls appeared. The base URL is nevertheless now an IP literal (`E2E_HOST`, default `127.0.0.1`), because the server binds only `127.0.0.1` and IPv6-first resolution of `localhost` adds a pointless failure path.

**Conclusion:** WebKit instability on the author's macOS machine is environmental (browser-process start-up/handshake under CPU starvation), not an application, library or server defect. It was _not_ hidden behind retries. WebKit is **not** skipped: it runs in CI on Linux, and locally it can be run with `E2E_BROWSERS=webkit`. Where local WebKit cannot launch, that fact is recorded in the acceptance record instead of being claimed as a pass.

## Concurrency and retry policy

| Profile   | Command                                                             | Workers | Retries | Browsers                           | Build                 | Purpose                                                |
| --------- | ------------------------------------------------------------------- | ------: | ------: | ---------------------------------- | --------------------- | ------------------------------------------------------ |
| `local`   | `pnpm e2e` (unchanged name)                                         |       4 |       0 | all (or `E2E_BROWSERS`)            | `always`              | day-to-day full run                                    |
| `focused` | `pnpm e2e:focused e2e/navigation.spec.ts -g Toolbar`                |       4 |       0 | chromium (override `E2E_BROWSERS`) | `reuse`               | developer loop                                         |
| `ci`      | `pnpm e2e:ci` (CI: `E2E_BUILD=skip pnpm e2e:ci` after `docs:check`) |       2 |       0 | chromium, firefox, webkit          | `always` (CI: `skip`) | **required before merging**; the CI-equivalent run     |
| `stress`  | `pnpm e2e:stress -g <pattern> --repeat-each=N`                      |       8 |       0 | all                                | `reuse`               | **diagnostic only**; exposes races, never a merge gate |

- Every value is explicit and overridable (`E2E_WORKERS`, `E2E_RETRIES`, `E2E_BROWSERS`, `E2E_BUILD`, `E2E_HOST`, `E2E_PORT`, `E2E_REPORT_DIR`, `E2E_OUTPUT_DIR`, `E2E_LOG_DIR`, `E2E_REUSE_SERVER`). Nothing depends on the machine's core count.
- **Retries are 0 in every profile.** A test that needs a retry to pass is a defect to investigate. Retries may only be re-introduced as an explicit, recorded decision (`E2E_RETRIES=2`), never silently.
- `scripts/e2e/run.mjs` prints the resolved configuration (commit, dirty flag, Playwright/Node versions, OS, CPUs, load, free memory, every `E2E_*` value) before running so a result can always be tied to its settings.
- The formal roadmap requirement of **five consecutive retry-free runs for the eventual RC is unchanged**; this milestone does not satisfy it.

## Reproducing

```bash
pnpm install --frozen-lockfile
pnpm exec playwright install --with-deps      # browsers
pnpm e2e:ci                                   # CI-equivalent: build + all three engines, workers 2, retries 0
E2E_BUILD=skip pnpm e2e:ci                    # exactly what CI runs after `pnpm build:demo && pnpm docs:check`

# a single area, one browser, existing build
pnpm e2e:focused e2e/navigation.spec.ts -g Toolbar

# stress a suspected race (diagnostic only)
E2E_BROWSERS=chromium,firefox pnpm e2e:stress -g "Toolbar" --repeat-each=40
```

Reports: `playwright-report/` (HTML), `e2e-logs/results.json` and `e2e-logs/preview-server.log`, `test-results/` (traces, screenshots, `diagnostics.json`).

## Non-goals (unchanged)

No new primitives, no website redesign, no change to the public API, no change to the consumer matrix (Angular 21.2 minimum / 21.2 / 22, strict AOT, installed tarballs, SSR, hydration, three engines, axe, CLI), no relaxed accessibility rules, no npm version bump or publication. The consumer suites keep their own `networkidle` helper (`consumer/e2e/helpers.ts`): that fixture app is a different application with its own readiness semantics and was deliberately not touched in this milestone.
