## 2. Findings per area

### Firefox

- `networkidle` is invalid as a readiness contract here (the deferred demo chunk is requested ~500 ms _after_ it resolves). All 8 uses in `e2e/` were replaced by the readiness contract. After the change the previously failing Firefox tests (docs health, both `forms-014` cases) passed 8 repeats at 8 workers (0 failures), the full Firefox suite passed in every run below, and `readiness.spec.ts` ("rapid navigation", 3 laps × 8 routes) passed 60/60 repeats at 8 workers on Chromium+Firefox.
- A Firefox-only failure appeared _during_ validation (run 2 of the first repeatability set, `home.spec.ts` "a successful copy is reported only after the clipboard resolves"). Trace analysis: the click took ~700 ms, so the stubbed 250 ms clipboard write had already resolved and the 2 s "Copied" window was running when the first assertion ran. It was a **test** race, not an application defect; the test now holds the write pending until released. 160/160 repeats pass at 8 workers (Chromium+Firefox). Those three runs are _not_ counted as clean evidence (see §4).
- Navigating away mid-load aborts in-flight lazy chunks (`NS_BINDING_ABORTED`). That must stay silent; `readiness.spec.ts` asserts no console/page error and no HTTP error, and permits only abort-class request failures.

### WebKit

- **Local WebKit could not be validated.** On the author's host, WebKit's runner process starts but never completes the inspector handshake: `browserType.launch` timed out (180 s inside the suites; 4 of 4 standalone launches at 60 s; again at 30 s with `caffeinate`), while Chromium launched in ~80 ms and Firefox in ~850 ms on the same machine. No test or server code is involved in that probe. Earlier in the session WebKit did run (run C: 304 passed in 2.8 min), so this is a degradation of the host, coinciding with heavy oversubscription by unrelated processes. The consumer WebKit cells (`consumer/e2e`, `consumer/e2e-cli`) failed the same way locally.
- The synchronized WebKit bursts in runs A–D show the request never left the browser (trace has no network entry for the hung `page.goto`) and no server-side error. The `localhost` vs `127.0.0.1` comparison was **inconclusive**; the base URL is now an IP literal anyway.
- An attempt to relaunch WebKit outside the command sandbox for diagnosis was **declined by the permission system and not pursued**. If the sandbox is what blocks WebKit's XPC services locally, that is for the maintainer to decide.
- **Not skipped, not waived:** WebKit stays in every profile and runs in CI on Linux. The WebKit acceptance for this milestone is whatever the GitHub Actions run below shows; locally it is "not verifiable on this host".

### Linux CI (all three engines, first retry-free run of PR #54, commit `62878f3`)

`E2E_BUILD=skip pnpm e2e:ci` on `ubuntu-latest` (4 vCPU): **966 tests, workers 2, retries 0 → 965 passed, 1 failed (WebKit), 16.1 min.** The uploaded `e2e-failure-diagnostics` artifact (trace, screenshot, server log, `results.json`) was enough to diagnose it without a rerun: `behavior.spec.ts` Combobox keyboard test, `aria-activedescendant` stayed on the first option after `ArrowDown`; runner load average 9.5 on 4 cores; no console errors, page errors, failed requests or bad responses.

Root cause (library): `ComboboxDirective.handleInput` scheduled `collection.first()` on the next animation frame to re-activate the first option once the filtered list rendered. When that frame lagged behind a subsequent `ArrowDown`, it reset the active option and undid the navigation. A minimal unit test with a held `requestAnimationFrame` reproduced it (`keeps keyboard navigation made before the post-typing frame runs`, failing before the change). The fix is internal: arrow keys and `setActive` bump an epoch and the pending reset stands down if the user moved the active option meanwhile. No public API, selector, input or output changed. This was invisible before because CI ran with `retries: 2`.

### Chromium

- Toolbar: two causes (static `data-ready` in the prerendered fixture; focusing before the reorder was rendered). No change to Core/Primitives keyboard semantics, no weakened assertion. `readiness.spec.ts` adds focused regression coverage: every `e2e-*` fixture's raw HTML must contain no readiness marker, and a deliberately slow app boot (all scripts delayed 400 ms) must show the prerendered Toolbar _without_ `data-ready`, then work with the keyboard once it appears.
- RTL submenu geometry: overlays are positioned on the next animation frame; the assertions are unchanged but now retry until both surfaces are placed (`expect.poll`).

### Production preview

Malformed percent-encoding in a URL killed the server (reproduced: `/%E0%A4%A` → uncaught `URIError`, all later requests `ECONNREFUSED`). Fixed and covered by `readiness.spec.ts`. Other changes (keep-alive, streaming, SIGTERM drain, build lock, completeness gate, `E2E_BUILD` modes) are defensive hardening documented in the roadmap; none of them was shown to change the WebKit symptoms, and none is claimed to.

## 3. Regression tests added

## 8. Remaining limitations and release blockers

- **WebKit is not verifiable on the author's machine** (see §2); CI is the only WebKit evidence for this milestone.
- The five-consecutive-retry-free-runs RC gate (all engines) is **not** satisfied.
- Retry-free CI acceptance depends on the GitHub Actions result for this PR; if it needs retries, they stay explicit and recorded, not silent.
- Open human gates, unchanged by this milestone: manual screen-reader matrix, genuine browser Autofill outside Chrome, formal acceptance of 0.17–0.19, the first guarded publication (npm `latest` is still `0.16.0`), the API-freeze decision, two independent real consumers.
- `consumer/e2e/helpers.ts` still uses `networkidle` (a different application, not in scope here); revisit when the consumer suites are next touched.
- This is not a statement that a 1.0 beta is ready.
