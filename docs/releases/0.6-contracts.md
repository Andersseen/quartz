# 0.6.0 — Contratos y medición

Estado: archivado como fase 0.6 preparada para release. Responsable de fase: orquestador.
Relación con roadmap: API-01…04, TEST-01…02 y DOC-01. Leer el
[protocolo](../roadmap/README.md) antes de asignar encargos futuros.

**Resultado:** alcance 1.0 explícito, contrato base y mecanismos que detectan regresiones.
**No incluye:** rediseñar Core, añadir componentes, adaptar Forms todavía, publicar npm.

## Orden de asignación

`06-01 → 06-02 → 06-03 → 06-05 → 06-06 → 06-08`.
`06-04` depende del inventario 06-01 y debe terminar antes de 06-08.
`06-07` depende de reconstruir correctamente la versión base y termina antes de 06-08.

## 06-01 — Inventario verificable de superficie pública

- **Responsable:** modelo de análisis; revisa orquestador. Solo documentación.
- **Leer:** ambos `packages/*/src/public-api.ts`, sus barrels y los tipos/directivas exportados;
  `cli/registry.js`, `docs/ai/CONTEXT.md`.
- **Trabajo:** generar una fila por símbolo exportado. Para cada directiva/componente registrar
  selector, host admitido, inputs/model/outputs y tipos. Para utilidades/refs registrar
  parámetros, retorno y lifecycle. Vincular archivo real; no deducir contrato de su nombre.
- **Salida propuesta:** `docs/api/public-surface.md`, agrupada por paquete y área.
- **Aceptación:** todas las exportaciones de ambos barrels están representadas; se diferencia
  API TypeScript de hooks DOM/CSS; cualquier símbolo sin consumidor o documentación queda señalado.
- **No hacer:** eliminar exports, cambiar private/public ni «normalizar» nombres.

## 06-02 — Decidir el catálogo estable y la ruta de cada export

- **Responsable:** producto + orquestador. No delegar la decisión al implementador.
- **Entrada:** inventario 06-01; catálogo candidato de ROADMAP; consumidores conocidos.
- **Trabajo:** asignar a cada área y export `incluido`, `retirar antes de 1.0` o `decisión
pendiente`. Justificar con uso/coste. Si un candidato necesita una API interna, decidir si
  debe permanecer interna; no exportarla automáticamente.
- **Salida propuesta:** `docs/api/v1-scope.md`, con migración para cada exclusión y responsable.
- **Aceptación:** cero decisiones pendientes antes del gate 0.6; ningún export retirado sin
  aviso y alternativa. Una retirada incompatible se ejecuta mediante spec propia en 0.x.

## 06-03 — Contratos por familia

- **Responsable:** orquestador diseña; modelo de documentación completa desde decisiones cerradas.
- **Leer:** `docs/ai/specs/_TEMPLATE.md`, specs existentes y código de la familia.
- **Dividir:** un encargo por Core, flotantes, selección, controles, disclosure y feedback.
- **Trabajo:** especificar estado inicial/control externo, vacío, disabled, métodos,
  secuencias de eventos, cleanup, teclado, ARIA y hooks. Registrar casos de entrada→resultado.
  Documentar diferencias intencionadas; no imponer uniformidad entre patrones distintos.
- **Salida propuesta:** specs `docs/ai/specs/v1-<family>-contract.md`.
- **Aceptación:** cada comportamiento tiene ID de requisito y aceptación observable;
  defaults, payloads y tiempos de emisión no quedan expresados como «consistente» o «correcto».

## 06-04 — Hacer fiable la cobertura

- **Responsable futuro:** implementador de tooling; revisa integrador.
- **Archivos de referencia:** `vitest.config.ts`, configs de proyectos, `package.json`,
  cobertura generada y job `unit-tests` del workflow. El escritor de configs es único.
- **Pasos:** confirmar comportamiento con la versión instalada; mover opciones globales al
  nivel correcto; eliminar opciones obsoletas; definir includes/excludes; medir por paquete;
  fijar baseline inicial y comprobación de no regresión; preparar subida gradual a metas 1.0.
- **Aceptación:** un archivo de lógica no importado figura descubierto; una caída bajo el
  threshold falla; un paquete no puede esconder caída con la cobertura del otro; el informe
  permite localizar archivo/ramas. No excluir lógica fuente para mejorar métricas.
- **Verificar:** suite con cobertura y una prueba temporal del gate que falle por su causa
  esperada; retirar el cambio temporal. No cambiar comportamiento de las librerías.

## 06-05 — Contrato de Forms antes de escribir adaptadores

- **Responsable:** orquestador; solo diseño en este encargo.
- **Entrada:** 06-02/03; controles existentes y sus models/outputs.
- **Resolver:** controles cubiertos, representación de vacío/mixed, disabled, touched,
  `writeValue`, reset, validación, precedencia entre binding model y Forms y eventos de commit.
- **Salida propuesta:** `docs/ai/specs/v1-forms.md`, con firmas/imports previstos y casos de
  ejemplo aprobados. Elegir la forma de distribución y peer dependency mínima; no inventar
  un paquete adicional si basta composición local.
- **Aceptación:** otro modelo puede implementar un adaptador sin decidir qué emite cada ruta;
  Forms no se filtra a Core. Si se decide signals-only, justificar y ajustar alcance/docs
  explícitamente; la recomendación actual es integración Forms opcional.

## 06-06 — Protección de tipos y templates públicos

- **Responsable futuro:** implementador de tooling; revisa orquestador.
- **Entrada:** 06-03/05 aprobados. Referencia: `scripts/verify-build.js`, declaraciones generadas
  y fixture en `scripts/consumer-smoke/fixture/`.
- **Dividir:** (a) inventario/diff de declaraciones; (b) casos TypeScript positivos/negativos;
  (c) casos de templates con compilador Angular. Diseñar mínimos, no una plataforma de tests.
- **Aceptación:** quitar un input/cambiar un tipo detecta diferencia; un binding inválido
  falla por diagnóstico esperado; un ejemplo correcto compila. La comprobación de nombres
  de `verify-build` se conserva como smoke, no se presenta como protección completa de API.
- **No hacer:** actualizar snapshots automáticamente para aceptar un cambio incompatible.

## 06-07 — Historia y migración base 0.5

- **Responsable:** modelo de documentación; revisa orquestador.
- **Archivos:** `CHANGELOG.md`, `docs/ai/STATE.md`, `README.md`, auditoría anterior y manifiestos
  en modo lectura.
- **Trabajo:** documentar selector `button[...]`, cambio del output de Switch, Tooltip
  interactivo y contexto de Tree. Separar versión del checkout de versión publicada si no hay
  evidencia del registro. Añadir ejemplos antes/después que se puedan compilar posteriormente.
- **Aceptación:** el lector de 0.4 puede identificar qué cambiar para la base 0.5 sin leer una
  auditoría interna; no se inventan releases ni fechas; no se incrementan versiones en este encargo.

## 06-08 — Integración y aceptación

- **Responsable:** integrador; producto/orquestador aceptan alcance y contratos.
- **Comprobar:** 06-01…07 cerrados, specs aprobadas, inventario completo y gates de cobertura/API.
- **Evidencia:** quality checks pertinentes, tests, builds, contract checks y changelog.
- **Salida:** acta breve con compromisos estables, decisiones tomadas, baseline y tareas Core
  listas. El implementador de 0.7 recibe sus specs, no una lista de problemas sin resolver.

**No avanzar:** si quedan candidatos sin clasificar, contratos de eventos abiertos o cobertura
sin medición fiable. Publicar 0.6 es una acción del responsable de release, fuera de estos encargos.
