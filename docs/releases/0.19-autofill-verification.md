# Genuine browser Autofill verification (0.19)

Closes the evidence gap left by 0.17 for the Volt parity row `autofill`: the synthetic `animationstart` tests prove the
detection pipeline, but not that a real browser puts a field into the state the directive listens for.

**Result: verified in real Google Chrome only.** Firefox and Safari/WebKit have no automation hook for autofill and were
not exercised; they remain on the manual procedure below. Quartz makes no universal autofill claim.

## What was run

| Item      | Value                                                                                                                                                                                                                               |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Date      | 2026-10-31                                                                                                                                                                                                                          |
| Browser   | Google Chrome 156.0.8078.80 (macOS), Playwright `channel: 'chrome'`, headed, fresh empty profile created by the run                                                                                                                 |
| App       | the installed-tarball consumer (`angular-21.2`, strict AOT, SSR + hydration) served by `scripts/consumer/run.mjs --stage serve`, page `/autofill`                                                                                   |
| Data      | one synthetic address ("Ada Example", `ada@example.test`, `+15555550100`, "1 Test Street", `00000`). No personal profile, no credentials, no payment data                                                                           |
| Mechanism | `Autofill.setAddresses` registers the address in the throwaway profile and `Autofill.trigger` asks **Chrome's own autofill engine** to fill the form. Chrome writes the values and applies `:-webkit-autofill`, not test JavaScript |
| Script    | `node scripts/consumer/autofill-real-browser.mjs --url http://localhost:<port> [--out file.json]`                                                                                                                                   |
| Evidence  | [`evidence/0.19-autofill-chrome.json`](evidence/0.19-autofill-chrome.json) (per-check results, Chrome version, timestamp)                                                                                                           |

Why the bundled Chromium failed before: Playwright's Chromium build has no DevTools `Autofill` domain
(`Autofill.trigger` → "wasn't found"). The branded Chrome channel has it. Firefox and WebKit builds expose nothing comparable.

## Limits of this evidence (read before relying on it)

- The fill is triggered through the DevTools protocol, not by a person selecting a suggestion from the autofill popup.
  It exercises Chrome's real autofill machinery, but not the popup UI.
- Only **address** fields in **Chrome on macOS**. Password managers, credit cards, Chrome on other platforms, Edge,
  Brave and third-party extensions are not covered.
- Detection depends on `:-webkit-autofill`/`:autofill` applying the documented CSS animation. In Firefox and WebKit the
  documented selector was confirmed to be **accepted by the engine** (the idle-field animation test in
  `consumer/e2e/autofill-lab.spec.ts` passes in all three engines), but nothing shows those engines emit it for real autofill.
- Quartz offers no promise for engines or credential managers that set values without a style change.

## Manual procedure (Firefox, Safari, or any real device)

Use a throwaway browser profile and fake data. Never use your personal profile, saved passwords or cards.

1. Serve the app: `pnpm build:lib && pnpm review:manual`; open `http://localhost:<port>/autofill` (URL printed).
2. **Chromium-based:** create a new profile (`--user-data-dir=$(mktemp -d)` or the profile switcher). Settings → Autofill → Addresses → add "Ada Example" with the fake data above.
3. **Safari:** use a fresh macOS user or Safari profile; add the fake contact in Settings → AutoFill → "My Info" (Contacts card). Safari offers AutoFill for contact fields on the page.
4. **Firefox:** use `firefox -P` with a new profile; Settings → Privacy & Security → Autofill → Saved addresses (availability depends on region) — if the browser offers no address autofill, record the engine as **not exercisable**.
5. Focus a field, accept the browser's suggestion, then read the page's "Observed state" section.
6. Record per engine: filled? `data-autofilled` on the fields? `autofilledChange` count/log? Forms value? Then use **Reset form values**, **Destroy fields** and the route link and record whether state cleaned up.
7. Put the outcome in row 14 of `docs/releases/0.17-manual-a11y.md` with browser/OS versions and a screenshot. A browser that fills fields without any `data-autofilled` change is a legitimate finding: record it as "fills, not observable".
